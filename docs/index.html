Content Refresh Prioritization

Using observable content, visibility, freshness, and engagement signals to prioritize pages for human review and possible content refresh.

Dhun Sehgal
Data Science | September 2026

Abstract

This project looks at whether observable content, visibility, freshness, and engagement signals can help identify which pages should be reviewed first for a possible content refresh. The analysis uses 30,000 anonymized page-level records and focuses on signals such as impressions, search position, CTR, content age, and engagement. A simple baseline ranking is compared with a Random Forest model using a client-level held-out test split to reduce the risk of leakage between related pages. The Random Forest reached a Precision@50 of 0.6200, compared with 0.3200 for the baseline, giving a 1.94× relative lift over the baseline. The resulting ranking is intended to support editorial review rather than automatically decide which pages should be changed.

1. Introduction / Problem Statement

When a website has a large number of pages, it can be difficult to decide which pages should be checked first for a possible content refresh. Some pages may still have good visibility but weak CTR, while others may be older or show signs of declining performance.

The goal of this project is to create a ranking that brings potentially important pages to the top of the review list.

The unit of analysis is a page. The output is a ranked list with a refresh-prioritization score, a reason, and a suggested action. A human editor can use this ranking to decide which pages to investigate first.

There are two possible costs to getting the priority wrong. Reviewing a page that does not need attention can use editorial time, while missing a page that deserves review can mean missing a potential improvement opportunity.

The approach combines several observable signals instead of relying on a single metric. The resulting score is used as a starting point for human review.

This analysis uses the anonymized starter dataset content_refresh_anonymized.csv, containing 30,000 page-level records and 44 original columns. The page-level starter dataset was used directly rather than querying the full warehouse release.

The dataset provides observable signals covering search demand, competition, content characteristics, visibility, traffic, freshness, and engagement. The performance features include 90-day and 30-day aggregate windows.

The analysis uses the page-level CSV as its data table. No warehouse tables were directly queried for the final capstone model.

The final model uses 21 features covering search demand, content size, visibility, freshness, CTR, position, engagement, and traffic signals.

These include search_volume, competition, cpc, word_count, char_count, impressions_90d, clicks_90d, pageviews_90d, sessions_90d, users_90d, engaged_sessions_90d, scroll_events_90d, content_age_days, days_since_last_update, ctr, avg_position, engagement_rate, scroll_rate, ai_traffic_pct, content_type, and main_intent.

Data exclusions and leakage checks

trend_direction was excluded because it was used to create the target. trend_pct was also excluded because it contains direct trend information. Using either field as a model feature could leak information about the outcome.

content_id was treated as an identifier and was not used as a feature. client_id was also not used as a feature; it was used only to create the client-level train/test split.

The final split contained no clients shared between the training and test sets, reducing the risk of client-level leakage.

No client names, domains, private queries, credentials, or other client-identifying information are included in the analysis or paper.

3. Methodology

The analysis starts with a simple rule-based baseline and then compares it with a Random Forest model.

Target

A page is labelled as declining when trend_direction is equal to down. All other pages are treated as non-declining.

Baseline

The baseline combines visibility, freshness, search position, and content depth signals. The final score is:

0.40 × visibility + 0.30 × freshness + 0.25 × position + 0.05 × depth

This provides a simple and transparent ranking that can be understood without a machine learning model.

Random Forest

A Random Forest classifier with 300 trees, random_state=42, and balanced class weights was used. Numerical features were median-imputed. Categorical features were filled using the most frequent value and then one-hot encoded.

Validation design

The evaluation uses GroupShuffleSplit with test_size=0.20 and random_state=42. The grouping variable is client_id, so pages from the same client are not placed in both the training and test sets.

The training set contains 23,837 pages from 25 clients, while the held-out test set contains 6,163 pages from 7 clients. There is zero client overlap between the two sets.

The declining base rate in the test set is 51.10%. Precision@50 should therefore be interpreted alongside the underlying class rate rather than on its own.

The Random Forest places 31 declining pages in its top 50 ranked pages, compared with 16 for the baseline. This corresponds to a 1.94× relative lift over the baseline.

5. Interpretation

The feature-importance results show that visibility, search position, content age, content length, and click-through behaviour were among the more informative signals in the model.

Some of the stronger features include impressions_90d, avg_position, content_age_days, char_count, word_count, and ctr.

Some simple relationships were weaker than might be expected. Word count and impressions had a weak positive correlation of about 0.163. The relationship between average position and CTR was also very weak, at about -0.073.

These results suggest that no single feature should be treated as the explanation for decline. The model combines several signals to create the ranking.

Feature importance shows which signals were useful to the model. It does not show that changing a particular feature will cause a page's performance to improve.

6. Limitations & Honest Framing

The main limitation is that the target represents an observed declining label. The model therefore learns to identify pages associated with that label rather than predicting what will happen after a future content refresh.

The model also does not explain exactly why a page declined. A high-ranked page should therefore be treated as a page worth investigating, not as proof that a specific change is needed.

This analysis is not a causal experiment. The results cannot be used to claim that refreshing a page will improve its future performance.

The results are therefore best treated as directional decision support for prioritizing human review.

These actions are starting points for human review. The final action should depend on the actual page, its intent, and the context behind its performance.

8. Reproducibility

The main analysis is available in the capstone notebook so that the complete workflow can be followed and reproduced. The repository contains the supporting assignment work, the capstone notebook, and the deployed research paper.

Repository: https://github.com/24f2001824/ml-flyrank

Capstone notebook: work/notebooks/capstone.ipynb

The main steps to reproduce the analysis are:

  1. Clone the repository.
  2. Open work/notebooks/capstone.ipynb.
  3. Make sure the anonymized FlyRank dataset is available at data/raw/content_refresh_anonymized.csv.
  4. Run the notebook from top to bottom.
  5. The notebook loads the data, creates the target, checks for leakage, creates the baseline, trains the Random Forest model, evaluates both methods, and generates the ranked recommendations.

The main Python libraries used include pandas, numpy, scikit-learn, matplotlib, and seaborn.

The random seed is fixed at 42 for the train/test split and the Random Forest model. The evaluation uses a client-level held-out test set with no client overlap between training and test.

The reported results are intended for decision support and should not be interpreted as causal evidence about search-engine ranking or the effect of making a content change.
